# PsycheAI plugin (with Psyche Pair)

The PsycheAI connector for Meta's Muse (and later ChatGPT), served at `app.psycheai.io`. It has two modes:
- **Know yourself (default):** Muse reads the user's own Instagram and writes their PsycheAI read (the Psyche Card and full report) to PsycheAI's own guide. The read is published to psycheai.io, and the user gets a private link to it. They answer no questions.
- **Psyche Pair (opt-in, one tap after the read):** the same read becomes a matching profile. The user checks it in one message and confirms it. Each week they see a few people who score above the bar and pick up to two. If both say yes, they chat privately or swap Instagram.

PLAN.md is the roadmap these were built from.

This README is the design log: why each behaviour exists. Update the relevant section with every behaviour change.

## Commands

```bash
npm run dev    # PSYCHE_DEV=1: adds POST /dev/signup, keeps state in .data.json
npm start      # production mode: hosts sign in with OAuth (no dev sign-in)
npm test       # tools/selftest.mjs — unit + HTTP integration checks, no network
```

One dependency (`@resvg/resvg-js`, for card images), no build step. Node 20+.

## Decisions

**Self first; dating is a module.** The MCP instructions (`CORE_MUSE`) cover only the PsycheAI read:
1. One go-ahead, before reading anything, that covers reading their Instagram (with or without their own side of their messages) and saving the read to PsycheAI as a private link. Buttons: *Yes, include my messages* / *Posts and stories only* / *Not now*.
2. `get_report_guide`, then read to its reading plan and write the read, quietly: no draft shown, no second ask.
3. `publish_psyche`.
4. One message: "Your Psyche is ready", with the card image and the link, then three buttons: *Ask about my Psyche Report* / *Sync with a friend* / *Find people who fit me*.

**The read comes first** (`start` in `lib/mcp.js`). The first menu offered all four things at once, Sync and Psyche Pair included, to someone with no read, and both need one. Now someone new is told what PsycheAI is and what they'll get (their character, type, the patterns that explain them, what drives them, what they need from people close to them; free, a few minutes, private), with the go-ahead in the same message (*Yes, include my messages* / *Posts and stories only*) and two questions answered in place: *What will I learn?* and *Is it private?*. Someone with a read (a card from the last 7 days, or a Psyche Pair profile) gets their news and *Ask about my Psyche Report* / *Sync with a friend* / *Find people who fit me* (or *See this week's matches*) / *Fresh Psyche Card and Report, with my messages* / *…, posts and stories only*. Asking for Sync or Pair without a read does the read first, then carries on. Muse also stopped at "connected… what would you like to do with it next?", so `start` and the instructions say to call it in the same turn as connecting.

Everything about dating (the one setup message, the matching fields, the weekly visit) is in `PAIR_MUSE`. That reaches the host only through `get_pair_guide`, once the user says yes. So a user who only wants their read is never asked about religion or kids. It also means dating can become a connector of its own if Meta approves PsycheAI but not dating.

**The read is PsycheAI's, written by Muse** (`lib/psyche.js`).
- **Guide:** `get_report_guide` fetches PsycheAI's read spec (sources, a reading plan, the standards, and the wellness, attachment and ideal partner standards Psyche Pair relies on) and its schema from `psycheai.io/api/import/guide`, cached for five minutes. The rules live in one place.
- **Publish:** `publish_psyche` sends Muse's answer and the user's name to `psycheai.io/api/import`, signed with `PSYCHEAI_IMPORT_SECRET`, which both servers share.
  - PsycheAI checks the answer exactly as it checks a provider's merged answer, seals it under a key it makes for it, and returns `psycheai.io/?m=<id>#<key>`.
  - A refused answer comes back with its problems, for Muse to fix silently.
  - The page opens the read in the browser with the key that never reaches either server, and keeps it there like any other read.
- **What this server keeps:** for 7 days, a card-level summary (character, why, headline, type, pattern names, top motivations, a few interests, Big Five scores) to draw the card image beside the link, then it's swept. Never the report.
- **Ask PsycheAI** for Muse reads is answered in Muse, from the read it wrote. There's no Gemini call on the Muse path.

**Muse fills the profile; we never see raw content.** We avoid the liability of holding anyone's posts, captions or messages. The host reads the user's Instagram and sends only structured fields. `validateProfile` drops any key that isn't in the schema, so there is nowhere for raw content to go. The summary shown to matches is written by the host under fixed rules: third person, no quotes, no employer, no other people.

**No swiping, minimal input, short chat.** "All input is error": the host already knows the user, so it does the work. The first visit is four messages from the host at most:
1. **Access:** one line asking for Instagram and Instagram messages.
2. **One message of buttons:** prefilled basics to glance at (from the Meta account, never from photos), plus who to meet, what they're after, religion (required), kids and marriage.
3. **"Your Psyche is ready":** their own card image, the link to the full read as a PDF, and "anything that doesn't sound like you?" with *Looks right* / *Change something*.
4. **One optional question:** what they're looking for, and any optional fields. Asked once, and skipping is fine.

Rules for every message: short, one idea, then the choice. Choices are buttons where the host has them, or a numbered list otherwise. Cards are shown as images, never described. Long text is never pasted into the chat. Each later visit goes in a fixed order: pending questions, intros, messages, this week's matches ("3 matches this week · 2 picks left", then the card images with a *Pick* button each), then the date check-in. Anything with nothing to show is skipped. The selftest pins these rules in the instructions.

**Dispute before matching starts.** After the card and the read, the user can disagree with any part. The host takes their word (at most one clarifying question, never arguing), changes the fields to `stated`, rewrites the affected parts of the read, saves, makes a new PDF if the read changed, and shows the updated card. This repeats until they say it looks right, and only then does `confirm_profile` put them in the pool. They can dispute anything later too.

**Only positive or neutral, and nobody is matched across a weak spot** (`lib/traits.js`, `lib/score.js`, `lib/card.js`).
- **Appreciates and turn-offs.** Each user has two short lists from a fixed vocabulary: calm, outgoing, homebody, adventurous, planner, spontaneous, ambitious, easygoing, expressive, reserved, active, creative, family, nightlife, drinker, smoker, spender, saver.
  - Each word is a test on the other person's profile (for example, "planner" means conscientiousness of 65 or more), read only from confident cells. Unknown is never a hit.
  - **A turn-off hit means never matched**, both ways. A guessed turn-off must have confidence of at least 0.6 to count; a stated one always counts.
  - **Each appreciated trait adds 2 points,** up to two each way, and the card says it warmly: "Jun is calm and a planner: the kind of person you're drawn to."
  - So a trait one person sees as a minus is only ever met by someone who sees it as a plus.
- **No weak areas.** Each dimension read from enough data (at least a third of its comparisons) must reach `AREA_FLOOR` (55, `PSYCHE_AREA_FLOOR`) on its own, however good the total, or the pair isn't put in a drop.
- **Cards never show a low score.** "Where you click" lists only areas at 70 or more, best first. One difference is worded as a balance ("One of you recharges out with people, the other at home: you can each bring the other somewhere new").
- **Banned wording:** `NEVER_SAY` (clash, incompatible, problem, tension, conflict, friction, struggle, weak, poor, bad) never appears in card wording, and the selftest checks every balance line and a full card against it.

**Card image and card page: two steps, two jobs.**
- **The image** (`lib/cardimage.js`, `/card/<token>.png`) is the glance inside the chat. It is PsycheAI's Psyche Card, redrawn here so it looks the same as one from psycheai.io: the character's scene and round crop, the line icons, the brand mark and the colour tokens all come from PsycheAI (`assets/psycheai.json`, written by `node tools/sync-psycheai.mjs`; rerun it when PsycheAI's art or palette changes).
  - **Your Psyche Card** (the psyche stage, after a read): 1080×1920, the same layout as PsycheAI's: character, name, headline, type, patterns, motivations, interests.
  - **A match card**: 1080×1350, the Psyche Card with their photo in the round and the fit % as a ring: first name and age, city, character, headline, pattern names, one "you two both…" line. That's enough to know whether you're curious, without reading anything in the chat.

  It's drawn as SVG and rendered to PNG with resvg and the bundled Inter font (`assets/fonts`, SIL OFL). Photos are fetched at render time from https, public addresses only, at most 5 MB, and not kept. Renders are cached in memory for 10 minutes.
- **The page** (`lib/pages.js`, `/m/<token>`) opens when the user taps. It shows the full profile for the stage the two are at, and only the one decision that stage asks for:
  - drop: *Pick*
  - picked: the fit by area as bars and the pattern names, then *Yes* / *No thanks*
  - mutual: about and career, then *Open private chat* / *Swap Instagram*
  - self: your own card as matches see it, with no buttons (changes go through the host so the card and the read stay in step)

  Every page the plugin serves (card pages, chat, sign-in, the email-link pages) uses PsycheAI's tokens and components (`lib/theme.js`), in light and dark, and links to the plugin's privacy section on psycheai.io. The buttons stick to the bottom of the screen. There's no script and no cookies. The link is signed (`lib/links.js`, HMAC under `PSYCHE_LINK_SECRET`, 14 days) for one viewer looking at one person, and what it shows is worked out live (`weekly.cardContext`), so the same link keeps working from drop to mutual. Anything the host can do with a tool, the page can do with a button, and the other way round.

**Consistency comes from the instructions, not from our own model.** No model of ours checks Muse's work, so `lib/instructions.js` fixes the procedure. Every scale has words at both ends. Confidence follows a fixed rubric (0.9 / 0.7 / 0.5, below that leave it empty). "Null, not a guess" is a rule. The field list in the instructions is generated from the schema, so the two can't drift.

**Every scored field is `{ value, source, confidence }`.** `source` is `observed` (Instagram), `stated` (the user said it) or `uploaded` (a file the user gave ChatGPT). This lets Muse profiles and ChatGPT profiles match against each other: each comparison counts by the weaker of the two confidences.

**Ask, don't infer, and religion is required.** The host is told never to infer sexual orientation, gender, age, ethnicity, religion, health, or plans for kids and marriage.
- **Religion is required:** a fixed list (muslim, christian, catholic, buddhist, taoist, hindu, sikh, jewish, free-thinker, atheist, agnostic, spiritual, other, or prefer not to say), asked in the first message.
  - "Prefer not to say" stays as an answer for people who won't share it. It counts as unknown, never as a mismatch, but it fails someone else's must-have on religion. Remove the option if you want it truly forced.
  - Religion counts in the score only when one of the two says it matters (importance ≥ 3). Close answers count as close: free-thinker, atheist and agnostic; christian and catholic.
- **Optional fields** (ethnicity, height, politics, drugs) are marked `statedOnly`. `validateProfile` refuses any value not marked `stated`, so a guess is dropped, never stored. These fields aren't scored on their own; they count only where someone makes them a must-have or a nice-to-have.
- **Why not guess when blank:** guessing special-category data is collecting it without consent (PDPA, GDPR), as far as I know it's against Meta's platform terms, and a wrong guess silently filters people out. Instead, if someone's must-have is on a field a strong match left blank, the match is held and asked openly, with the field's own options and *skip* ("Would you like to add your ethnicity to your profile? Some of your strongest matches care about it."). This uses the custom-question queue and its 3-a-week limit, and they're never told who asked. Diet may be read from posts like any other field.

**The user confirms before anything is matched** (after the dispute step above). `save_profile` stores a draft. Only `confirm_profile`, called after the user's clear yes, makes it live, and only live profiles enter the pool.

**"Who I want" is parsed by the host.** The user describes their ideal match in their own words. The host turns that into must-have and nice-to-have rules over the same field keys, reads them back, then saves them. This costs us nothing and keeps the parsing next to the user, who can correct it. `set_preferences` returns the pool size so a must-have that empties the pool is visible straight away. A must-have on a field the other person left empty **passes**. Otherwise common gaps, like smoking left empty, would quietly empty the pool.

**Scoring is code, not a model.** It's cheap enough to run on every pair, and it gives the same answer every time.
1. **Filters, both ways:** same mode, each seeking the other's gender, each inside the other's age range, same city, compatible intent, the kids deal-breaker (wants vs doesn't want), each side's must-haves, and blocks.
2. **Seven dimensions:**
   - **needs:** attachment, love languages crossed (A's giving against B's receiving), closeness, and reassurance against expressiveness.
   - **lifestyle**, **future**, **communication**, **values**, **background:** education, life stage, family closeness and upbringing.
   - **personality:** similarity on openness, conscientiousness and extraversion, plus the level of agreeableness and steadiness.
3. **Weighted average by mode** (`WEIGHTS` in `lib/score.js`). Dating leans on needs, future and lifestyle. Friends leans on lifestyle and values.
4. **Pulled toward 50 when the pair shares little data,** so two thin profiles can't clear the bar on a lucky overlap.
5. **Each side's nice-to-haves** add up to +5. **Attraction bucket:** +3 for the same bucket, −3 for different (dating only).

**Attraction comes from behaviour, never from a model judging photos.** A person's bucket is above or below the pool median of how often their card is picked when shown, smoothed, and only after 20 showings. A model rating faces would bring in bias, wouldn't pass Meta's review, and is a legal risk. The bucket is never shown to anyone. It nudges the score; it never blocks a match.

**Two picks a week; answering doesn't use a pick.** The scarcity makes each pick count. The limit is on reaching out, so a popular person isn't forced to ignore people who picked them. If both pick each other, it's mutual straight away. Pending intros lapse after 14 days. A declined pair never meets again.

**Cards reveal in stages.**
- **In the drop:** one photo, first name, age, city, headline, the character badge ("Odysseus · ENFJ"), fit %, and one "you two both…" line.
- **When someone picks you:** the fit by area as bars, up to three photos, why they are their character, and their three signature pattern names.
- **When it's mutual:** the short write-up, the career line, the private chat, and the Instagram swap state. Each person chooses, per match, whether to offer their Instagram (`share_instagram`). Handles appear to both only once both have offered. Until then the other side sees "they offered", which is a gentle nudge.
- **Never shown:** the bucket, must-haves, raw values, email.

**Joining from a read on psycheai.io** (`lib/join.js`). For people who made their read the upload way (and ChatGPT users, who are sent there for it), and for Muse readers whose read went deeper when they added WhatsApp or Google there.
- **"Use for Psyche Pair"** on psycheai.io: after the reader agrees, the page posts a card-level subset of the read (type, Big Five scores, attachment lean, love languages, interests, values, motivators, character, headline, pattern names, confidence) to `app.psycheai.io/join` as a top-level form post. Only those fields are read from it; anything else is dropped unread. It's held an hour under a random id, then the usual sign-in (email code, Google or Apple). A new email makes an account.
- **What it fills:** the matching traits it supports, source `uploaded`, at the read's confidence (0.9 / 0.7 / 0.5 from its score; attachment one step lower, as the softest thing a read says), checked by `validateProfile`. Never a stated-only or sensitive field. Also the card summary for the card image (30 days) and the first name, headline and pattern names if the draft has none.
- **Stated always wins.** A deeper read replaces uploaded and observed traits, never stated ones, on the draft and on a live profile. `save_profile` keeps uploaded traits the host doesn't send, so Muse adds to the read rather than starting over. The host then shows the card to check and asks what only the user can answer, as for anyone.

**Muse Sync: how two people sync, friends, family, anyone** (`lib/sync.js`). Separate from Psyche Pair and never about dating.
- **Both ask.** "Sync me with @jun" calls `sync_with`; Jun says yes by asking back (same tool), on a nudge in Muse or the digest. Someone not on PsycheAI yet gets an invite Muse can send in an Instagram message, with the user's OK. Asks wait 30 days, at most 10 open at once. No thanks (`remove_sync`) is silent.
- **Consent at the first Sync.** The first call returns an ask, shown word for word: PsycheAI keeps the card-level profile from their latest read (`psyche.summarize`: character, type, Big Five, patterns, motivations, interests, values, how they show care) and their Instagram handle, until they delete it. Never posts, messages or the report.
- **Handles stay out of keys.** The handle comes from the Instagram account connected to Muse. Asks and the handle index are keyed by an HMAC of it (`store.handleKey`), as emails are. One handle, one account: a second claim is refused.
- **No score, as on psycheai.io.** A Sync is read, not rated. `get_sync` hands Muse PsycheAI's own Sync prompt, brief and schema (`GET /api/import/guide?kind=sync`, with a Muse preface), the two card-level profiles, and the derived facts worked out here the way PsycheAI's `prompts.derivedFacts` does (exact shared interests, values and motivators, Big Five gaps, type axes). Muse writes it in the chat in PsycheAI's Sync tone. Nothing it writes comes back here.
- **The Sync card** (`/card/<token>.png`, kind `sync`) is drawn in the Psyche Card design: both characters, both names and types, what they share, and "a natural pair" when their characters are in each other's syncs. Nothing in common reads as "plenty to show each other", never as a gap. Its page has no buttons.

**The 28 Psyche characters, as a badge.** These are PsycheAI's catalogue and its sync table, unchanged. Which characters are open to someone comes from the gender they *stated*, so nothing is judged from photos: women get a woman's or a neither character, men a man's or a neither, and nonbinary people one of the four neither (Baymax, The Tin Man, Remy, Pikachu). `validateProfile` refuses a character outside the user's side. If the two characters are in each other's syncs, the card says "Mulan and Po are a natural pair". That's a talking point only and never touches the score. Characters are named alone, never with their studio.
- **IP risk:** most of the 28 belong to Disney, Marvel, Nintendo, Sanrio and others. A name-only comparison on a commercial dating card is a real risk, more than it was for a personality quiz. Have a lawyer look before launch. The public-domain ones (Odysseus, Sherlock Holmes, Dr Watson, The Tin Man) are safe.

**The full private Psyche read, delivered as a PDF.** The host writes the full PsycheAI report and hands it over at once as the private PDF link (below), with the user's own card. Nothing is pasted into the chat paragraph by paragraph. It contains:
- character and why, summary, three signature patterns
- type and Big Five, all ten motivations ranked
- interests, values and beliefs
- relationships (attachment, love languages, disagreement, the partner who suits them)
- wellbeing, a development plan
- the roast, last

Career is left out. It's insight and coaching, never therapy. It's only for the user and never used on a match's card.

**Instagram and Instagram messages, with permission.** Step 0 asks once for access to the user's Instagram and Instagram messages, with one line on why. From DMs the host reads only the user's own side: how someone talks to the people closest to them says the most about needs, communication and attachment. The other person's words are never used or sent. Once a match is mutual and both share Instagram, the host can draft an opener with the user and send it by Instagram DM, but only once they approve the exact words. The ChatGPT procedure has no such step.

**10 to 20 interests,** each a plain common word or two ("hiking", "k-dramas"), so they overlap across people. Four shared interests counts as a full match on that comparison. After a date, the host asks once whether they met and would meet again. `log_date` stores only those two answers, for calibration. Any reflection stays in the chat.

**Custom questions for must-haves the profile can't answer** (`lib/questions.js`). Take "must be okay with pet reptiles". The host adds a yes/maybe/no question to a shared bank and uses it as a must rule (`q.<key>`).
- **Unknown holds the pair back,** unlike ordinary must-haves. The question is queued only for people who would otherwise clear the bar, and their host asks it openly, as a question that sharpens their own matches.
- **Nobody is named.** The asker is never named, and never sees the answer, only who reaches their drop.
- **Scoring:** yes passes, maybe passes at −5, no fails.
- **Answers are reused.** They're kept on the answerer's profile, so one answer serves every later asker.
- **Limits:** at most 3 questions handed to a host per person per week. Unanswered ones lapse after 14 days and aren't asked again for 60. Topics in `BANNED` are refused: sex, money, race, religion, health, bodies, kids and marriage (which have their own fields), legal status and politics.
- **Why not a hidden test:** asking under false pretences breaks trust and Singapore's PDPA purpose rule, and wouldn't pass review.
- **The keyword filter is a first line.** It over-blocks a little ("short trips"). Add a model check before launch.

**In-app chat, for people who'd rather not hand over Instagram** (`lib/chat.js`). This is the one place we hold words people wrote, so:
- **Sealed:** each message is sealed with AES-256-GCM under `PSYCHE_CHAT_KEY`. The store never sees text, and a box only opens in its own chat.
- **Nobody reads it** unless one of the two reports the other. A report keeps the thread for 90 days for review instead of letting it be deleted.
- **Deleted:** messages go after 30 days. The whole thread goes when either person ends it, blocks without reporting, or deletes their data.
- **Notifications:** new messages go into the daily digest (below), folded into one line per match.
- **Where users read it:** the host (`get_messages`) or the no-script web page linked from the mutual email.
- **Through the host:** messages read in Muse pass through Meta, so the privacy page must say so.
- **Instagram is swapped per match,** never by default (see cards above).

**Everything happens in the host; email is only a nudge** (`lib/notify.js`). Neither host can notify someone, so events (someone picked you, it's mutual, a new message) wait in a list per person, and any visit clears it, because the host shows the same things. Every visit, the host checks intros, messages and pending questions. Once an hour, `digest()` emails one summary to each person who has something waiting, hasn't visited for 24 hours, and hasn't had a digest for 24 hours. So it's at most one email a day, never while they're using the app, and each event is sent at most once. The digest also says when this week's matches are ready, without making the drop. Its intro lines carry one-time yes/no links, and its chat lines a personal chat link.

**OAuth sign-in** (`lib/oauth.js`), as the MCP authorization spec asks:
1. A host calling `/mcp` without a token gets 401 with `resource_metadata`.
2. It finds us through the two `/.well-known` documents and registers itself (dynamic client registration, https redirects only).
3. It sends the user to `/oauth/authorize` with a PKCE S256 challenge. The user types their email, gets a 6-digit code (10 minutes, 5 tries, 5 codes an hour per email) and types it back.
4. The host swaps the one-time code and its verifier for a 30-day access token and a refresh token. Refreshing rotates both.

**One-tap Google and Apple sign-in** (`lib/social.js`) sit above the email code on the same page, and each is on only when its client id is set.
- **Google:** the authorization code flow. The code is swapped at Google's token endpoint with `GOOGLE_CLIENT_SECRET`.
- **Apple:** the ID token is posted back to us (`form_post`), so signing in needs only the Services ID (`APPLE_CLIENT_ID`).
- **Checks:** every ID token is verified against the provider's published keys (RS256 for Google, ES256 for Apple, cached for an hour), along with issuer, audience, expiry and the nonce kept on the sign-in request. Only a verified email is used, and Apple relay addresses are fine.
- **One finish:** both end in the same `signedIn` step as an email code, so the host gets its one-time code the same way.

These are our own accounts, so one email is one account across Muse and ChatGPT. Every code and token is stored only as a hash. `/dev/signup` remains for `npm run dev` only.

**The private read as a PDF** (`lib/reads.js`). The host sends the read's sections once, as part of "Your Psyche is ready". We seal them under a fresh key and keep only the sealed box, for 7 days. The link is `/read/<id>#<key>`. Browsers never send the part after `#`, so we can't open what we store. The page opens it in the browser, and "Save as PDF" uses the browser's own print to PDF, which works on phones too. Privacy-page wording: the read passes through our server in memory to make the link, and what's stored is encrypted with a key we don't keep.

**Signature patterns and motivations.** The profile carries the three signature pattern names from the private read (names only; the lines and evidence stay in the read), shown once someone picks you. It also carries the top three of Schwartz's ten motivations, scored in the values dimension by distance around Schwartz's circle: the same motivation scores 1, a neighbour 0.8, the opposite side 0. The circle wraps, so universalism sits next to self-direction.

**Text only.** Muse can see images, so the read and the Psyche Pair profile are written from words and dates alone (captions, comments, messages, the bio, words on a story, posting times), never from the photos or videos themselves. PsycheAI's spec says the same. The one use of a photo is choosing three for the match card (face visible, alone), and nothing about the person is read from them.

**No sign-in to type** (`oauth.authorize`). Muse signs in to any connector that offers sign-in, so the account can't be skipped, but it can be invisible: authorize makes an account on the spot, with no email and no code, and sends Muse its code at once, so *Connect* opens and closes by itself. A signed, HttpOnly cookie (`pp_account`, 400 days, path /oauth) brings the same browser back to the same account on a reconnect; a tampered or missing one makes a new account, never someone else's. Email sign-in is still there: `?signin=email`, or `PSYCHE_EMAIL_SIGNIN=1` for everyone (for Meta's review, whose reviewer account signs in by email). **Three photos, chosen by them, kept as sealed copies** (`lib/photos.js`). Because Muse follows tool results more closely than the guide, the times are in what tools return too: start's intro ("takes about 5 to 10 minutes"), each Yes button's own `say` (the wait line, word for word), the returning menu's line on how long each choice takes, and the next step after the card. start's description says to call it before replying to a new connection. Whether Muse calls a tool before its own "connected" message is up to Muse; the rest is ours. One wording was taken back the same day: start's note said to say the wait line "and nothing else until the card is ready", and a result that tells the assistant to stay quiet about what it's doing reads like an attack to a safety check (a run stopped on a tool result right after the Fresh button); it now says only to say the line.

**A button back to Muse on a phone.** With the invisible account, connecting was a bare redirect from the authorize page straight to Muse's return address. On a phone the sign-in runs in a browser sheet, and iOS and Android only hand an address to an app when someone taps it, so the sheet sat on a page with nothing to press. On a phone (by its user agent) the authorize page now says "You're connected" with one *Back to Muse* button carrying the code; a computer still goes straight back.

**Client ID metadata documents, so a phone needn't ask.** Muse's phone app asks the user for a Client ID, because it doesn't register itself (`/oauth/register`) the way Muse on the web does. The MCP authorization spec's newer answer is a client ID metadata document: the host's client_id is an https address, and the JSON there names the host and its return addresses. We advertise it (`client_id_metadata_document_supported`), fetch the document when a URL client_id first arrives (https, public addresses only, no redirects, 64 KB, 5 s; refreshed at most daily), check that it names itself and lists only https return addresses, and keep it with the registered clients (`loadMetadataClient`). Whether Muse's phone app uses it is up to Meta; until it does, `psycheai` in the Client ID box works, and psycheai.io/muse says so.

**Any Client ID works.** Muse's phone app shows a "Secure credentials store" sheet with a Client ID box and no hint of what to type, and it does so before it talks to us, so client ID metadata documents didn't remove it. Most people would stop there. So any printable ID someone types (a guess, "PsycheAI", a stray space) is the public client under that name, with the public client's rule: it returns only to Meta's own hosts, so a made-up ID can't send a sign-in code anywhere else. A blank one is still refused. The hint itself goes where people see it: psycheai.io/muse gives a message to copy into Muse that names the Client ID, which Muse may fill in as it fills the address.

**A fixed client ID for hosts that ask for one.** Muse's "Add custom connector" on mobile asks for a Client ID rather than registering itself. The answer is `psycheai` (`oauth.PUBLIC_CLIENT_ID`): a public client with no secret, PKCE required, as for a registered one. Since anyone can use a shared ID, it returns only to https addresses on Meta's own hosts (muse.ai, meta.ai, meta.com, facebook.com, instagram.com and their subdomains), so a sign-in code can't be sent elsewhere. A refused address is named on the error page and in the log; add it with `PSYCHE_PUBLIC_REDIRECT_HOSTS` (hosts) or `PSYCHE_PUBLIC_REDIRECT_SCHEMES` (app schemes) once it's confirmed to be Meta's.

**Tool titles and hints** (`LABELS` in `lib/mcp.js`). Every tool carries a plain title ("Publish your Psyche", "Pick a match") and MCP's annotations, which hosts use to decide what to show and what to ask about first. Reads are `readOnlyHint`; everyday actions change only the user's own things and are not destructive; only `delete_my_data`, `end_chat` and `remove_sync` are `destructiveHint`. As a custom connector, Muse blocked every unlabelled tool that might write, including the read itself; the labels give it what it needs to decide. The selftest pins the destructive set.

## Calibration: what the fit % means

The fit % people see is not the raw score. It is the pair's rank among all eligible pairs in the pool, so the number always means the same thing (`lib/calibrate.js`):

| fit | means |
|---|---|
| 80 | top 5% of pairs |
| ~90 | top 1% |
| ~97 | top 0.1% |

The cold-start reference was last regenerated when appreciates and turn-offs joined the score: 95th percentile 72, median 64.

The formula is `fit = 100 − 20·√((1 − p) / 0.05)`, capped at 99.

**Why rescale:** with 400 random profiles (40,000 pairs), raw scores bunched between 51 and 67 (median 59), and only 0.01% reached a raw 80. A fixed raw bar would leave nearly every drop empty, and the number would mean nothing to users.

**The reference** is every eligible pair in the pool once there are 500 of them. Until then it's a seeded synthetic pool (`tools/calibrate.mjs` prints `DEFAULT_REFERENCE`).

**Rank alone is not enough.** In a weak pool, the top 5% can still be poor matches. So a match must also clear `RAW_FLOOR` (66 by default, about the top 30% of random pairs, `PSYCHE_RAW_FLOOR`). If nobody clears both, the drop is empty and says so. That's deliberate: the point is to end dating fatigue, and showing no one beats showing the wrong one. Must-haves are hard filters, so they can empty a drop too.

**After launch,** tune `WEIGHTS`, the similarity tables and `RAW_FLOOR` against outcomes: picked, accepted, and "did you meet?". Re-run `tools/calibrate.mjs` only to refresh the cold-start reference.

## Running it

Production is one Render web service (`render.yaml`) at **app.psycheai.io**: a CNAME from the psycheai.io DNS to the Render service, with Render issuing the certificate.
- **Storage:** Upstash Redis (`UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`), encrypted at rest. Every value is sealed with AES-256-GCM under `PSYCHE_STORE_KEY`, bound to its collection and key, so a leaked Upstash token or backup is unreadable. Without the key, the server refuses to start against Upstash. Emails live in their own collection, never on the user record, and are looked up by an HMAC of the address, so even Redis field names don't show one. This doesn't protect against a compromised server, which holds the key. State lives in memory and is written through to Redis within about 200 ms of each change, one hash per collection (`pp:users`, `pp:intros`, …). It's read back on start and flushed on SIGTERM, so deploys and restarts lose nothing. Run one instance only: two would overwrite each other.
- **Email:** Resend (`RESEND_API_KEY`, `MAIL_FROM` on a domain verified in Resend). Without a key, emails only go to the log.
- **Secrets:** `PSYCHE_STORE_KEY` encrypts the store, and must never change once data exists. `PSYCHE_LINK_SECRET` signs card links. `PSYCHE_CHAT_KEY` seals chats: any string, and it must never change once chats exist. Render generates both. 
- **Free plan:** Render's free instance sleeps after about 15 idle minutes. An UptimeRobot monitor on `https://app.psycheai.io/health` every 5 minutes keeps it awake. A free workspace has about 750 instance hours a month, enough for one always-on service, so keep PsycheAI in another workspace or on a paid plan. Hosts give up on slow servers, so don't let it sleep.
- **Muse:** the connector address is `https://app.psycheai.io/mcp`.
- **Public pages** live on psycheai.io (psycheai repo, `docs/`): `/muse` (what PsycheAI in Muse is, how to add it, Plus, safety), `/muse-privacy`, `/muse-terms` and `/muse-docs` (connecting, sign-in and every tool). The plugin's old addresses (`/`, `/add-to-muse`, `/privacy`, `/terms`, `/safety`, `/docs`) answer 301 to them (`lib/site.js`), so links already handed out keep working. All noindex and out of the sitemap until launch.
- **Directory review:** `SUBMISSION.md` has the form answers and steps. `PSYCHE_REVIEWER_EMAIL` and `PSYCHE_REVIEWER_CODE` (six digits) turn on a reviewer account (`lib/demo.js`): the fixed code signs in that email only, and on start the server seeds it with a read, a confirmed profile, demo matches, someone who picked them and a Sync. Demo people are flagged `demo` and only ever match each other (`weekly.candidates`). Remove both settings after the review.

## Money: Psyche Pair Plus

Neither Muse nor ChatGPT lets a connector sell digital goods today, and OpenAI's guidelines reportedly also bar indirect upsells. So nothing is sold, priced or offered inside the hosts, and the selftest checks the instructions and tool descriptions for it. A limit is stated as a limit ("at most 1 custom must-have"), never as a reason to upgrade.

- **The plans** (`lib/plans.js`). Free: 2 picks a week, a drop of up to 5, 1 custom must-have, and everything else (the read, Sync, answering people who pick you, chat, the Instagram swap). Plus, US$4.99 a month or US$29 a year: 5 picks, a drop of up to 8, 5 custom must-haves. Matches still have to clear the same bar, so Plus shows more of the people who fit, never people who don't. A bigger drop starts with the next week's drop.
- **Buying it** (`lib/plus.js`). psycheai.io/muse links to `app.psycheai.io/plus`, which signs in with the same email code, Google or Apple as the hosts (`oauth.startWeb`). Only an account that already exists can sign in there; a new email is told to add PsycheAI to Muse first. Sign-in lands on `/plus/<token>`, a signed link for that account that lasts an hour (no cookies, as with the card pages), with Stripe Checkout for a year or a month, or Stripe's billing portal to manage or cancel.
- **Stripe, without the SDK.** Checkout and portal sessions are REST calls with fetch. Price ids come from `STRIPE_PRICE_MONTHLY` / `STRIPE_PRICE_YEARLY`, so prices change in Stripe; the page shows the agreed prices (`SHOWN`). Plus is off until `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and both prices are set.
- **Only a signed webhook changes a plan.** `/stripe/webhook` checks the Stripe-Signature HMAC over the raw body, within five minutes. The return from Checkout changes nothing. Subscription events carry the account id in their metadata and set `user.plus` = `{ customer, subscription, status, until, cancelAt }`. Active, trialing and past_due count as paid (Stripe retries the card) until the period end plus 3 days; cancelled or unpaid don't. No card details are ever here.
- **Deleting an account cancels its subscription at Stripe first.** If Stripe can't be reached, nothing is deleted and the user is told to try again.
